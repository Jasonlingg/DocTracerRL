# Session Writeup — RL Portfolio Project Exploration (2026-09-01)

## Starting point

Coming into this session, the prior project (DocTracerRL / rlm-explorer) had stalled: GRPO training on multi-hop QA showed a flat reward curve, traced to three compounding causes — sparse/fuzzy reward (F1 across a whole multi-step trajectory, poor credit assignment), a badly undersized SFT warm-start (21 examples vs. literature norms in the thousands), and a task (multi-hop QA synthesis) that may have exceeded a 7B LoRA model's raw capability ceiling. The goal for this session was to design a new, better-scoped RL project for the portfolio, informed by that failure.

---

## Project 1: Code-Triage Router — fully designed, spec'd, and planned

### What it is

Train Qwen2.5-7B-Instruct with GRPO to triage AI-generated code diffs into one of four actions — `SHIP`, `RUN_TESTS`, `LINT_TYPECHECK`, `ESCALATE_STRONG_MODEL` — using a binary-gated, cost-aware reward (`reward = task_success × (K − λ·cost) − format_penalty`, directly modeled on Salesforce's xRouter). The task was chosen because it fills a specific resume gap: neither Preference Model (designed RL *environments*) nor Assort Health (built the *pipeline* around a fuzzy-anchor entity-resolution decision) involved personally training an RL *policy* end-to-end.

### Research grounding established

- **xRouter (Salesforce AI Research, arXiv 2510.08439)** — the methodological anchor. Important correction made mid-session: initial citations overstated its evidence. On direct inspection of the full paper, it contains **no training curves, no before/after comparison for the untrained vs. trained 7B model, and no simple-baseline comparisons** — its own authors state *"the most significant disappointment concerns the sophistication of learned routing behaviors."* This was flagged honestly rather than left uncorrected.
- **Rewards as Labels (Zhai et al., Feb 2026, arXiv 2602.05630)** — formalizes RLVR as classification (verifiable rewards partition rollouts into correct/incorrect sets, i.e., binary labels). Used as the theoretical grounding for "RL as a general classification-training recipe."
- **TruthRL (arXiv 2509.25760)** — precedent for ternary/asymmetric reward shaping (correct / abstain-escalate / wrong).
- **SWE-PRBench / SWE-Review-Bench** — frontier models catch only 15–31% of human-flagged issues on diff-only review. Used as honest context, not a primary claim to beat.
- **"Cognitive Overhang" framing** — added to pre-empt the objection "why not just always use the best model": a ~50–250x cost gap and ~10x throughput gap between frontier and budget-tier models, compounding badly across an agentic loop's many sequential calls.
- **CodeRabbit/Greptile differentiation** — added explicitly to the spec: those are PR-level *reviewers* (read a diff, explain what's wrong); this project's router is a cheaper *decision layer* sitting in front of that, for in-session triage during active agentic coding, not after-the-fact PR review.
- **Reward-hacking / shortcut-learning research (arXiv 2604.15149, "LLMs Gaming Verifiers")** — a late but important finding. Confirmed a real risk the user identified independently: if mechanical signals (`test_pass`) trivially predict the correct label, the model can learn to exploit that shortcut instead of genuinely reading the diff. **Fix added to the spec:** at least 20% of training examples must have signals that do *not* trivially predict the label (tests pass but the diff is still wrong; tests fail for unrelated reasons but the diff is fine), plus a required "shortcut-detection check" in eval that scores accuracy on this subset in isolation.

### Deliverables produced this session

1. **Spec:** `docs/superpowers/specs/2026-08-27-code-triage-router-design.md` — full design doc covering motivation, why this task over alternatives (rejected: garbled-voice-entity escalation, chess-via-GRPO, negotiation/Werewolf), the reward formula, data pipeline, training approach, evaluation design, success criteria, deliverables, demo/write-up assets, SMART goals (4-week schedule), and risks. Iteratively revised in-session to add: Cognitive Overhang framing, CodeRabbit/Greptile differentiation, and the shortcut-resistance requirement.
2. **Implementation plan:** `docs/superpowers/plans/2026-08-28-code-triage-router.md` — 15 TDD-structured tasks covering repo scaffold, data schemas, mechanical labeling, SWE-bench-style and git-history data sources, dataset assembly with task-disjoint splitting, baseline policies, the reward function, SFT warm-start, GRPO training with a mandatory cheap-diagnostic gate ($5 before $50), the five-policy eval harness with transcript logging, a Claude Code skill wrapper (`/ship-check`), and — added late — a stretch task to quantize the final checkpoint to 4-bit GGUF and package it for Ollama so it runs on a laptop CPU.
3. A known, explicitly-flagged gap: the shortcut-resistance requirement was added to the spec *after* Tasks 4, 7, and 12 of the plan were written, so those tasks need a follow-up update (a companion function to `hindsight_label` for constructing signal-label-mismatch examples, plus the shortcut-detection subset scoring in the eval harness) before execution.

### Why this project was ultimately not committed to

Sustained, well-founded doubt surfaced repeatedly across the session: the task is fundamentally a **single-shot classification decision** (diff in, one label out), which the user determined is not genuine RL in the sense of trial-and-error exploration they experienced building RL environments at Preference Model — it's reward-shaped classification wearing RL's mechanics. This was independently confirmed as a real, named failure pattern in the literature (RLVR models "abandon rule induction and enumerate instance-level labels" when a cheap correlated signal exists). The user's core standing objection, stated explicitly late in the session: **"I don't think RL is the right tool for classifier stuff."** This is treated as a settled design constraint for any future project, not an open question.

Additionally, the user determined the underlying domain (reading and judging code correctness) requires a level of code comprehension that may exceed a small model's actual capability — the same failure shape that killed the prior chess-via-GRPO idea — and this was never fully resolved (a proposed cheap zero-shot probe to test it was explicitly declined by the user in favor of continuing to search for a better task).

**Status: fully built, ready to execute, but not the currently favored direction.**

## Other directions seriously explored and set aside

For each, the reason for setting it aside is recorded so it isn't re-litigated from scratch later.

- **Negotiation / business bargaining (GRPO + RULER).** Strong, *verified* research backing — unlike xRouter, this one was checked in full and holds up: a real paper (arXiv 2604.09855) shows a trained 30B agent going from 0.0126 → 0.7664 reward and 73.44% → 91.99% deal rate, with a concrete transcript (untrained agent caves to $56, trained agent holds to $30 on the same product). Passes the "no classifier" rule (genuine multi-turn, open-ended dialogue with real state change). Set aside because the user said negotiation itself didn't produce the "wow" factor for them personally, despite the strong evidence.
- **Preference-Arena Harness → RL** (inspired by Design Arena, a real $8M-raised YC startup doing crowdsourced Elo-style AI-output voting). Idea: build a mini pairwise-preference voting harness, then RL-train a model off the collected preference signal — connects directly to the user's actual Preference Model background. Set aside (for now) because the domain was never chosen and the real bottleneck (getting enough outside voters for a credible "preference" signal) was never resolved.
- **Countdown/math-style GRPO reproduction (TinyZero-style).** The "guaranteed clear signal" option — extremely well-precedented (~$30, hours of training, dozens of public reproductions), zero risk of an ambiguous null result. Rejected by the user as not clickbaity/differentiated enough — "everyone's done this."
- **Poker / Liar's Poker.** Real, well-documented precedent for RL beating even elite humans (arXiv 2511.03724, "Solly"). Rejected because the user does not play poker and didn't want to spend a month in a domain with no personal interest.
- **Custom tokenizer optimization** (train a specialized sub-word tokenizer for a low-resource language/domain jargon). Considered and rejected as too small/lateral a project — no RL, doesn't fill the resume gap, more of a weekend exercise than a flagship project.
- **Inference optimization** (quantization, distillation, KV-cache optimization, custom kernels). Recognized as connecting to the user's existing GPT-2 Inference Engine resume project, but assessed as its own large, multi-specialization category better suited to a *future*, separate project (potentially: distilling the eventual trained router itself) rather than something to start now.
- **Cross-model KV-cache transfer** (NVIDIA research topic). Investigated via a "what would the demo look like" exercise; concluded it requires white-box access to both models' internals, which structurally rules out escalating to closed frontier APIs — the demo would necessarily be small-open-model-to-larger-open-model, a real but different and much heavier systems project. Not pursued; noted as a possible one-paragraph "future work" mention only.
- **Sports/event forecasting via RL (Brier score, Polymarket/Metaculus-style).** Real, large-scale precedent exists (arXiv 2604.26733: 110K resolved events; arXiv 2604.15719: GRPO + Brier score on a 120B model, Metaculus gains). The user raised a sharp and correct objection: "beating the market" is likely an information-access problem, not a training problem, and RL cannot manufacture information the model doesn't have. This was validated as correct — the honest, defensible version of this project would target *calibration* (is the model honestly uncertain, not overconfident) rather than *predictive accuracy beating aggregated market information*. Not pursued further after this correction, though the calibration framing remains available if revisited.
- **Natural-language-to-code compiler + RL for reliability**, inspired by discovering the startup **ProgramAsWeights (PAW)** and its underlying paper. This became the seed for the current leading direction (see below).

## Discovery: ProgramAsWeights (PAW) and Professor Yuntian Deng

Investigated in depth after the user surfaced `programasweights.com`. Key findings, verified via the actual GitHub repo, README, architecture docs, and the underlying paper (arXiv 2607.02512, "Program-as-Weights: A Programming Paradigm for Fuzzy Functions"):

- PAW is **not** a code-generation compiler as first assumed — it's a **hypernetwork**: an English spec is turned into a "pseudo-program" by an untrained 4B model, a second *trained* compiler model extracts hidden states from that pseudo-program, and those hidden states are directly projected into LoRA adapter weights (A/B matrices) — predicting what a fine-tuned model's weights would look like, in one forward pass, without ever running real gradient descent. The resulting adapter (~5–22MB) is bundled with a tiny frozen base model (Qwen3-0.6B or GPT-2-124M) and runs 100% locally, no further LLM calls.
- Authors: Wentao Zhang, Liliana Hotsko, Woojeong Kim, Pengyu Nie, Stuart Shieber, Yuntian Deng — Waterloo, Cornell, and Harvard affiliations. Trained on a 10M-example dataset called FuzzyBench.
- The user's target professor was confirmed as **Yuntian Deng**, Assistant Professor at the University of Waterloo's Cheriton School of Computer Science (the user's own school). PhD from Harvard, previously a postdoc at AI2. His research centers on NLP, multi-agent systems, and — the throughline across his actual publication list (WildChat, WildBench, implicit chain-of-thought, "Control-Data Flow Separation" for multi-agent LLMs, and PAW itself) — **compiling or distilling expensive, explicit computation (a spec, a multi-step reasoning chain, a multi-agent conversation) into something compact, cheap, and reusable.**
- This was connected to the user's own, independently-formed production insight from Assort Health: *"it was better for the agent to write code and query, rather than keep grepping repeatedly"* — recognized as structurally the same idea Deng's lab studies, just arrived at from real engineering experience rather than research literature.

Separately, real market/industry validation was found for the broader pattern PAW exemplifies: fine-tuned, narrow, specialized sub-models genuinely do outperform frontier models at production tool-calling tasks (AWS example: 77.55% pass rate on ToolBench vs. 26.00% for ChatGPT-CoT), and multi-tier caching of such sub-models is documented to cut production LLM costs 40–86%. This confirmed the "compile a reusable specialized tool once, reuse it" instinct is mainstream, proven industry practice — PAW's specific hypernetwork mechanism is the novel, unproven part, not the underlying "specialize and reuse" pattern itself.

## Current leading direction (not yet formally spec'd)

**Working idea:** An agentic RL harness where an agent receives natural-language requests (PAW-style: fuzzy search, format repair, extraction, classification, log triage — general data/utility tasks, chosen over a specific domain like sports or documents so training data is easy to generate at scale and the framing stays close to PAW's own stated use cases) and must **write and execute its own code, live, in a sandbox, as its tool-calling mechanism** — rather than selecting from a fixed menu of predefined tools. This was arrived at after explicitly ruling out every "pick from a small set of discrete actions" design as **not genuine RL** — a hard constraint the user set late in the session: *"I don't think RL is the right tool for classifier stuff."* Writing arbitrary code is open-ended and generative, satisfying that constraint directly, and mirrors the user's actual Preference Model / DocTracerRL environment experience (agent writes code in a persistent REPL, observes real execution output, decides its next action based on genuinely new information).

**Reward design agreed so far:** `correctness × (1 − efficiency_cost)` — correctness is checked mechanically via auto-generated test cases per task (no LLM judge), and gates the reward entirely (a fast wrong answer scores at or near zero, carrying forward the reward-banking lesson from the original DocTracerRL project and the code-triage reward design). Among correct solutions, lower efficiency cost (a combination of measured runtime/complexity and token/code-length cost) scores higher. This was explicitly chosen over the alternative of tracking correctness and efficiency as separate, un-combined metrics.

**Framing:** positioned as directly inspired by and extending Professor Deng's PAW research — PAW compiles a static neural function from a spec via a hypernetwork; this project trains an agent, via RL, to solve the same class of "turn a natural-language ask into something executable" problems by writing and running live code, optimized explicitly for the correctness and efficiency (speed, token cost) properties central to Deng's research thread. Intended both as a strong portfolio piece in its own right and specifically as a credible signal of fit for research under Deng, whom the user wants to work with.

**Infrastructure to reuse (not rebuild):** the existing `PersistentREPL`, corpus/environment scaffolding, and TRL/GRPO/RunPod training pipeline already built and validated during the code-triage project (and originally from DocTracerRL) — the plan is to change the task and reward, not the underlying training/execution machinery, avoiding a repeat of the infrastructure-debugging time sink from earlier sessions (pip dependency hell, disk space issues, peft version mismatches — all already solved and documented in the pinned `requirements-pod.txt` workflow).

**Not yet decided / next steps:**
1. The exact task-generation pipeline for the natural-language utility requests (how they're synthesized, how auto-generated test cases are produced per task, how difficulty/variety is controlled).
2. Whether the environment is single-step (one request → one piece of code, run once) or genuinely multi-step (agent writes code, sees output, revises) — the multi-step version is more clearly "real RL" under the user's stated constraint and more consistent with the DocTracerRL-style environment shape being reused, but was not explicitly confirmed in-session.
3. SFT warm-start data volume and source (the lesson from DocTracerRL — 21 examples was fatally undersized — must be explicitly re-applied here).
4. Whether/how to explicitly connect this project's write-up to Deng's PAW paper as a citation and point of comparison (e.g., comparing the RL-agent approach's efficiency/correctness against PAW's own reported numbers where feasible).
5. This has not yet gone through a full brainstorming-to-spec pass the way the code-triage project did — a formal design document does not yet exist for this direction. A brainstorming session for it was started in this session but was interrupted before a domain/task decision was finalized, and no spec has been written yet.
